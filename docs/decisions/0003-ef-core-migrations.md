# 0003 テーブルの変更を EF Core Migrations で管理する

決めた日: 2026-10-17

## 状況

旧版は、Flyway の名前の付け方(`V{連番}__{説明}.sql`)の SQL を V1 から V11 まで持ち、NestJS 版では自作の実行の仕組みで適用していた。
バックエンドを .NET で作り直すにあたり、テーブルの変更をどう管理するかを決める必要があった。

## 決めたこと

EF Core Migrations で管理する。
V1 から V11 の最終の形を、最初のマイグレーション 1 つにまとめる。
初期データは `HasData` でマイグレーションに含める。
バックエンドは起動のときに未適用のマイグレーションを適用する。

## 理由

- 利用者が EF Core Migrations を選んだ。
- エンティティの構成とテーブルの形を、C# のコードの 1 か所で持てる。構成とテーブルの食い違いを、マイグレーションを作るときに EF Core が差分として出す。
- Flyway のコンテナを compose に足さなくて済む。

## 却下した案

- **V1 から V11 の SQL を残し、Flyway のコンテナで適用する**: 旧版の SQL をそのまま使え、旧版の `CLAUDE.md` の決まりとも合う。エンティティの構成と SQL の 2 か所でテーブルの形を持つことになる。
- **V1 から V11 を、EF Core のマイグレーションに 1 つずつ写す**: 履歴が残る。V9 のように途中で座標の単位を変えた手順まで写すことになり、新しく作るデータベースには要らない。

## 影響

- 旧版のデータベース(`game.flyway_schema_history` を持つもの)は、そのままでは使えない。2026-10-17 に、利用者が旧版の記録を移さずに捨てると決めた。手元のボリュームを消して作り直す手順は、[データベースの共通仕様](../design/common-database.md) 5.5 に書く。
- `CLAUDE.md` の「Flyway で管理する」と「`V{連番}__{説明}.sql`」の決まりを、EF Core Migrations の決まりに置き換えた。
- 適用を起動のときに行うので、バックエンドを複数動かすときは見直す([データベースの共通仕様](../design/common-database.md) 5.5)。
