# 0011 サービスの中をクリーンアーキテクチャで分ける

決めた日: 2026-10-17

## 状況

最初の設計([サービスの共通構成](../design/common-service.md) の旧版)では、バックエンドを 1 つのプロジェクトにし、層をディレクトリで分けていた。
層の間の向き(エンドポイントからリポジトリへの一方向)は、決まりとテストの文字列の検索で守る形だった。
利用者が、クリーンアーキテクチャで実装することを求めた。

## 決めたこと

各サービスを Domain、Application、Infrastructure、Api の 4 つのプロジェクトに分ける。
頼る向きは、プロジェクトの参照で Api と Infrastructure から内側へだけにする。

## 理由

- 利用者が選んだ。
- 層の間の向きを、決まりではなくプロジェクトの参照で守れる。Domain と Application が EF Core と ASP.NET Core を参照しないことを、ビルドの時点で保証できる。
- 業務の規則(日と段階の組の重複、段階と収縮先の種類の対応、座標の範囲)を、データベースも HTTP も使わずに単体テストで確かめられる。
- サービスを機能ごとに分けた(決定の記録 [0012](0012-split-services-by-feature.md))ので、どのサービスも同じ形にしておくと、行き来して読みやすい。

## 却下した案

- **1 つのプロジェクトのまま、ディレクトリで層を分ける**: プロジェクトの数が少ない。層をまたぐ参照を、ビルドが止めない。
- **Application をユースケースごとのクラス(命令と処理の対)に細かく分ける**: 1 つの操作が 1 つのクラスになり、追いやすい。機能の数に対してクラスとファイルの数が増えすぎる。機能ごとのサービスのクラスにする。

## 影響

- プロジェクトの数が、サービスごとに 4 つとテスト 1 つ、共通の部品 2 つになる。
- [サービスの共通構成](../design/common-service.md) の 5.1 から 5.3 を書き直した。
- 層の検査(`AC-SVC-06`)は、テストの中の文字列の検索をやめ、Domain と Application の参照するアセンブリを確かめる形にした。
