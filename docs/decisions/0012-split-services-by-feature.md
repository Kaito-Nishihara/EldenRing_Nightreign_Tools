# 0012 バックエンドを機能ごとに 3 つのサービスに分ける

決めた日: 2026-10-17

## 状況

最初の設計では、Gateway の後ろのバックエンドを 1 つのサービスにしていた。
利用者が、機能ごとにサービスを分けることを求めた。
どの単位で分けるか、データとサービスの間の呼び出しをどう持つかを決める必要があった。

## 決めたこと

バックエンドを次の 3 つのサービスに分ける。

| サービス | 受け持つ機能 | 持つデータ |
|---|---|---|
| `master-service` | マスタの取得、マスタの管理 | 夜の王、地変、開始地点、収縮候補地、第二収縮地点、拠点候補地、夜ボス |
| `record-service` | プレイ記録、パターン検索 | 記録、収縮先 |
| `relic-service` | ビルドシミュレーターの効果のマスタ | 遺物の効果の分類、効果、ランク |

PostgreSQL のコンテナは 1 つのままにし、サービスごとにデータベースと利用者を分ける。
サービスの間の呼び出しは、`record-service` から `master-service` への一方向だけにする。

## 理由

- 利用者が選んだ。
- パターン検索は記録を集計するだけなので、記録と同じサービスに置き、記録の持ち主を 1 つにする。分けると、パターン検索が別のサービスのデータを読むか、記録を写し取る仕組みが要る。
- 遺物の効果は、ほかのどのデータとも関わらないので、そのまま分けられる。
- マスタを消さずに非表示にする(決定の記録 [0013](0013-hide-masters-instead-of-delete.md))ので、`master-service` が `record-service` へ参照を問い合わせる必要がなく、呼び出しが一方向になる。
- PostgreSQL を 1 台にすると、手元で動かす重さが増えない。データベースと利用者を分ければ、ほかのサービスのデータに触れられない。

## 却下した案

- **1 つのサービスのまま、中を機能ごとに分ける**: データベースの外部キーで記録とマスタの整合を守れる。利用者が機能ごとの分割を求めた。
- **4 つに分ける(記録の保存とパターン検索を分ける)**: 機能と 1 対 1 になる。パターン検索が記録のデータを読むために、記録のサービスへの問い合わせか、記録を写す仕組みが要る。
- **サービスごとに PostgreSQL のコンテナを分ける**: 分離が強い。手元で PostgreSQL が 3 つ動く。

## 影響

- 記録からマスタへの外部キーはなくなる。記録を保存するとき、`record-service` が `master-service` の内部の API で、参照する行があるかを確かめる。
- パターン検索の応答に収縮先の名前と座標を入れるため、`record-service` が `master-service` に問い合わせる。`master-service` が応答しないときは 503 を返す。
- Gateway は、パスで 3 つのサービスへ振り分ける。
- テーブルの変更と初期データは、サービスごとのマイグレーションで持つ(決定の記録 [0003](0003-ef-core-migrations.md) の V1 から V11 のまとめは、サービスごとに分けて行う)。
- サービスの間の整合をデータベースで守れないので、記録が非表示のマスタを参照することがある。画面は非表示のマスタも名前で出す。
- 記録の数が増え、パターン検索のたびのマスタへの問い合わせが重くなったら、`record-service` にマスタの写しを持たせる形を考える。
