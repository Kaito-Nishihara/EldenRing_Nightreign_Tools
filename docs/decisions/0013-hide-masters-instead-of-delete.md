# 0013 マスタを消さずに非表示にする

決めた日: 2026-10-17

## 状況

最初の設計では、記録から参照されている開始地点、収縮候補地、第二収縮地点を消そうとすると 409 で拒み、参照されていなければ実際に消していた。
参照の確認は、データベースの外部キー(`ON DELETE RESTRICT`)で行っていた。
サービスを分けた(決定の記録 [0012](0012-split-services-by-feature.md))ので、マスタと記録が別のデータベースになり、外部キーで確かめられなくなった。

## 決めたこと

管理の画面の「削除」をやめ、「非表示にする」と「表示に戻す」にする。
非表示の行は、プレイヤー向けのマスタの一覧と、新しい記録の入力から外す。
行そのものは消さない。

## 理由

- 利用者が選んだ。
- 消さなければ、`master-service` が `record-service` へ参照の件数を問い合わせなくてよい。サービスの間の呼び出しが一方向になり、`record-service` が止まっていても管理の操作ができる。
- 過去の記録が指すマスタが残るので、非表示にした収縮候補地を含むパターンも、名前と座標で表示できる。
- 誤って非表示にしても、表示に戻せる。

## 却下した案

- **今の仕様どおり、参照されていれば 409 で拒む**: 不要な行を消せる。`master-service` が削除の前に `record-service` へ問い合わせる形になり、サービスが互いを呼ぶ。`record-service` が止まっていると削除できない。
- **参照されていなければ消し、されていれば非表示にする**: 不要な行が残らない。2 つの動きがあり、どちらになるかが利用者に分かりにくい。参照の確認のために問い合わせが要る点も変わらない。

## 影響

- 開始地点、収縮候補地、第二収縮地点、拠点候補地のテーブルに、非表示にした日時(`hidden_at`)を足す。
- 管理用の `DELETE` の API をやめ、修正の入力に `isHidden` を足す。
- [マスタの管理](../design/master-admin.md) の受け入れ条件のうち、削除と 409 のものを書き直した。
- 決定の記録 [0005](0005-keep-play-records.md) の「記録が参照するマスタを消せない」は、外部キーではなく、この決定で守る。
- 不要な行が増えたら、記録から参照されていない非表示の行を消す保守の手順を考える。
