# 0015 ステージングと本番では、配置の前にマイグレーションを適用する

## 状況

各サービスは、起動のときに自分のデータベースへマイグレーションを適用している(データベースの共通仕様 5.5)。
同じサービスを複数同時に起動すると適用が競合するので、データベースの共通仕様は「増やすときは適用の仕方を見直す」としていた。
AWS では、同じサービスのタスクを 2 つ以上動かし、入れ替えの間は古いタスクと新しいタスクが同時に動く(決定の記録 [0014](0014-deploy-to-aws-ecs.md))。

## 決めたこと

ステージングと本番では、サービスごとのマイグレーションの束を、配置の前に ECS の単発のタスクで 1 回だけ走らせて適用する。
サービスは起動のときに適用しない。
手元の compose は、今のとおり起動のときに適用する。

## 理由

- 適用するのが 1 つのタスクだけになり、競合しない。
- 適用に失敗したら、サービスを入れ替えずに止められる。古いタスクが動き続けるので、利用者に影響しない。
- 適用の前にスナップショットを取る段を、パイプラインの中に置ける。
- 手元では、起動するだけでデータベースができる今の手軽さを残せる。

## 却下した案

- **起動のときに適用し、EF Core のロックで競合を防ぐ**: 競合は防げるが、適用に失敗したタスクは起動に失敗し、入れ替えの途中で止まる。スナップショットを取る段を置けない。
- **GitHub Actions のランナーから RDS に直接つないで適用する**: RDS を外から届く所に置くか、ランナーを VPC の中に置く必要がある。
- **SQL の台本(`migrations script`)を人が流す**: 人の手順に頼ると、順序と適用の漏れが起きる。台本は PR のレビュー用に添えるだけにする。

## 影響

- サービスに、環境変数 `Database__MigrateOnStartup`(既定は `true`)を足す。ステージングと本番では `false` にする。
- マイグレーションは、1 つ前の版のコードでも動く形で書く(CI/CD と AWS への配置 6.3 の互換の規則)。
- データベースの共通仕様 5.5 に、この決定への参照を足す。
