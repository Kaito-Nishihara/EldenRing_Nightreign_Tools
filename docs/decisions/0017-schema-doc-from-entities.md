# 0017 テーブルの定義書をエンティティから作る

決めた日: 2026-10-18

## 状況

仕様書にテーブルの定義書がなかった。
列の型と制約は EF Core のテーブルの設定に、意味は機能ごとの仕様書に散っていて、1 つのテーブルの全体を 1 か所で見られなかった。
手で定義書を書くと、エンティティを変えたときに直し忘れ、コードと食い違う。

## 決めたこと

列の説明を Domain のエンティティの XML ドキュメントコメントに書き、それをデータベースのコメントにし、EF Core のモデルから定義書の Markdown を作る。

## 理由

- 利用者が選んだ。
- 説明を書く所がエンティティの 1 か所になる。エンティティを読む人と、データベースを直接見る人と、定義書を読む人が、同じ説明を見る。
- 型、文字数、NULL、キー、索引、制約は、EF Core のモデルにすでにある。定義書のためにもう一度書かなくてよい。
- XML ドキュメントコメントは C# の言語の機能なので、Domain が EF Core を使わないままでいられる(決定の記録 [0011](0011-clean-architecture.md))。
- CI で作り直して比べれば、直し忘れを PR の段階で見つけられる。

## 却下した案

- **定義書を手で書く**: 道具が要らない。エンティティを変えるたびに直す手間がかかり、直し忘れを見つける手段がない。
- **データベースにはコメントを入れず、定義書にだけ説明を載せる**: 説明を変えてもマイグレーションが増えない。データベースを直接見たときに説明が出ない。
- **説明を EF Core のテーブルの設定(`HasComment`)に書く**: XML の読み込みが要らない。説明がエンティティから離れ、エンティティを読む人の目に入らない。
- **動いているデータベースから定義書を作る(SchemaSpy など)**: データベースの実物と必ず合う。作るたびにデータベースを起動する必要があり、CI が重くなる。

## 影響

- Domain のプロジェクトで XML ドキュメントのファイルを出力する。サービスの実行の時にも、このファイルを Domain の DLL の隣に置く。
- 説明を変えると、そのサービスにマイグレーションが 1 本増える。
- テーブルの定義書は `docs/database/` に置き、仕様書のサイトにも載せる。
- 説明のない列を足すと、テストが落ちる。
