データベースの更新

ステージングと本番では、サービスの起動のときにマイグレーションを適用しない。 配置の前に、単発のタスクで 1 回だけ適用し、失敗したらサービスを入れ替えない(決定の記録 0015)。 手元の compose は、今のとおり起動のときに適用する。

配置のときの順序

  1. マイグレーションの束を作るmain
    サービスごとに dotnet ef migrations bundle で、マイグレーションを 1 つの実行ファイルにまとめ、イメージとして ECR へ送る。
  2. RDS のスナップショットを取る本番だけ
    手動のスナップショットを取り、終わるまで待つ。名前にタグの版を入れる。 取れなければ、ここで止める。
  3. master、record、relic の順に、1 つずつ適用する
    ECS の単発のタスクで束を走らせる。各サービスは自分のデータベースの利用者で適用する。 1 つでも失敗したら、残りを適用せず、サービスを入れ替えない。古いタスクが動き続ける。
  4. サービスを入れ替える
    サービスは Database__MigrateOnStartup=false で起動し、適用しない。入れ替えの間は、古いタスクと新しいタスクが同じデータベースを使う。
  5. 配置の後の確かめ
    今ある API を呼んで応答を確かめる。本番では記録を保存しない。

マイグレーションの互換の規則

入れ替えの間は古いコードと新しいコードが同時に動き、コードだけを前の版に戻すこともあるので、マイグレーションは 1 つ前の版のコードでも動く形にする。

変更やり方出す回数
列やテーブルを足すそのまま足す。NOT NULL の列は既定値を付ける1 回
列やテーブルを消す先にコードから使うのをやめて出し、次の版で消す2 回
列の名前や型を変える新しい列を足して写し、コードを替え、後の版で古い列を消す2 回から 3 回
制約を強める今ある行が満たすことを確かめるマイグレーションを先に出す2 回
記録の行を消す書かない(決定の記録 0005)なし

PR でのマイグレーションの検査

検査落とす条件受け入れ条件
作り忘れdotnet ef migrations has-pending-model-changes が、モデルとマイグレーションの食い違いを見つけたAC-CD-01
書き換えmain にあるマイグレーションのファイルが変わった(スナップショットを除く)AC-CD-02
壊す変更DropTable、DropColumn、RenameColumn、RenameTable があり、db-breaking の印がないAC-CD-03
前の版からの適用main の版に初期データと試しの記録を入れたデータベースへ、PR のマイグレーションを適用できない
空からの適用空のデータベースに、すべてのマイグレーションを適用できないAC-DB-01

PR には、足したマイグレーションの SQL(dotnet ef migrations script --idempotent)を成果物として添え、レビューで読めるようにする。

戻し方

データベースは戻さず、コードだけを戻すのが基本である。マイグレーションの互換の規則で、前の版のコードが新しいデータベースで動くためである。

失敗戻し方誰が
新しいタスクがヘルスチェックを通らないECS の配置のサーキットブレーカーが、前のタスク定義へ戻す(AC-CD-09)自動
配置の後に誤りが見つかった配置のワークフローを、前の版のコミットの値で走らせる利用者
マイグレーションが途中で失敗したサービスは入れ替わっていない。直したマイグレーションを足して出し直す利用者と Claude
データが壊れた配置の前のスナップショットか、指定時刻への復元で新しいインスタンスを作り、切り替える利用者

本番で Down のマイグレーションは走らせない。
