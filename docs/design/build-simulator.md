# 機能設計: ビルドシミュレーター

## 1. 目的

プレイヤーが、遺物の通常効果と深層効果を選び、効果を重ねたときの合計を確かめられる。
プレイの前に、遺物の組み合わせを比べる用途を想定する。

## 2. 範囲

やること:

- 通常効果 3 枠と深層効果 3 枠の選択
- ランクのある効果のランクの選択
- 計算の種類ごとの合計の出し方と、表示の桁
- 遺物の効果のマスタの取得の API

やらないこと:

- 遺物そのもの(名前、色、セットの効果)の管理。今のマスタは効果の単位で持っている
- 祝福の選択。旧版の画面設計にあったが、マスタがない
- 夜の王の弱点との相性の表示
- 選んだ組み合わせの保存と共有の URL(8 章)

### この文書で使う言葉

| 言葉 | 意味 |
|---|---|
| 効果 | 遺物に付く 1 つの効果。例: 物理攻撃力上昇 |
| 深層効果 | 深き夜の遺物に付く効果。デメリットを伴うことがある |
| 計算の種類 | 効果を重ねるときの合わせ方。`multiply`、`percent_add`、`flat_add`、`special` |
| 属性 | 効果がかかる対象。例: `physical`、`fire`、`strength` |

## 3. 画面

パス: `/build`
試作: [画面: ビルドシミュレーター](../screens/build.md)

### 3.1 効果の枠

- 通常効果の列に 3 枠、深層効果の列に 3 枠を置く。
- 各枠で、効果を選択の欄から選ぶ。欄の中は分類(能力値、攻撃力、カット率など)ごとにまとめる。
- 通常効果の枠には `is_deep` が偽の効果、深層効果の枠には真の効果だけを出す。
- ランクのある効果(`rankMax` が 0 より大きい)では、ランクのボタンを出す。初めのランクは `rankMin` とする。
- 深層効果で、選んだランクの `hasDemerit` が真なら、「この段からデメリットが付く」を `ember` の色で出す。
- 効果がデメリット(`effectSign` が `negative`)なら、枠の下の説明を `ember` の色にする。
- 「すべて外す」で 6 枠を空にする。確かめの枠は出さない。保存していないので失うものが少ないためである。

### 3.2 効果の合計

選んだ効果を、計算の種類と属性の組でまとめて合計する。

| 計算の種類 | 合わせ方 | 表示 | 例 |
|---|---|---|---|
| `multiply` | すべての値を掛ける | `×` と小数 2 桁 | 1.05 と 1.15 → `×1.21` |
| `percent_add` | すべての値を足す | `+` と小数 1 桁と `%`。0 で終わる小数は省く | 4 と 6 → `+10%` |
| `flat_add` | すべての値を足す | `+` と整数。単位が `per_sec` なら `/秒` を付ける | 100 と 100 → `+200` |
| `special` | 合計しない | 効果の名前と、発動の条件だけを出す | |

- まとめる鍵は、属性があれば「計算の種類と属性」、なければ「計算の種類と効果の識別子」とする。
- 合計の結果は分類ごとに区切り、分類の並び順(`sort_order`)で並べる。
- 値が 1 より小さい掛け算と、負の足し算は `ember` の色で出す。
- 各行の下に、どの枠の何が合わさったかを小さく出す。

計算はブラウザで行う(決定の記録 [0006](../decisions/0006-build-calc-in-browser.md))。

### 3.3 状態

| 状態 | 出すもの |
|---|---|
| 読み込み中 | 6 枠分の骨組みの表示 |
| 何も選んでいない | 合計の列に「効果を選ぶと、ここに合計が出ます」 |
| エラー | 共通仕様 3.9 と 3.10 のとおり |

## 4. API

### `GET /api/v1/relic-effects`

受け持ち: `relic-service`
必要な役割: なし

**出力(200)**

```json
[
  {
    "id": 12,
    "categoryId": "attack",
    "categoryNameJa": "攻撃力",
    "categorySortOrder": 1,
    "nameJa": "物理攻撃力上昇+0〜4（深層）",
    "isDeep": true,
    "effectSign": "positive",
    "calcType": "percent_add",
    "attribute": "physical",
    "stackable": "yes",
    "rankMin": 0,
    "rankMax": 4,
    "conditionJa": null,
    "notesJa": null,
    "ranks": [
      { "rank": 0, "value": 4, "unit": "percent", "hasDemerit": false },
      { "rank": 3, "value": 10.5, "unit": "percent", "hasDemerit": true }
    ]
  }
]
```

- 並びは分類の `sort_order`、効果の `id` の順とする。
- `ranks` はランクの小さい順とする。値のない効果(`special`)の `value` は `null` とする。
- 旧版の出力に `categorySortOrder` を足す。画面で分類を並べるためである。

**エラー**

想定するエラーはない。
共通の 500 だけである。

## 5. データ

持ち主: `relic-service`(データベース `nightreign_relic`)
読むだけで、書かない。

| テーブル | 主な列 |
|---|---|
| `relic_effect_categories` | `id`、`name_ja`、`sort_order` |
| `relic_effects` | `id`、`category_id`、`name_ja`、`is_deep`、`effect_sign`、`calc_type`、`attribute`、`stackable`、`rank_min`、`rank_max`、`condition_ja`、`notes_ja` |
| `relic_effect_ranks` | `effect_id`、`rank`、`value`、`unit`、`has_demerit`。`(effect_id, rank)` は一意 |

初期データは旧マイグレーション V11 から移す([データベースの共通仕様](common-database.md) 5.6)。

## 6. サービスの間のやり取り

画面を開いたときに 1 回だけ取得する。
以後の計算で API を呼ばない。
画面 → Gateway → `relic-service` の順に呼ぶ。
`relic-service` は、ほかのサービスを呼ばない。

## 7. 受け入れ条件

| 識別子 | 条件 |
|---|---|
| `AC-BLD-01` | `GET /api/v1/relic-effects` が、V11 の効果をすべて返し、各効果の `ranks` がランクの小さい順である |
| `AC-BLD-02` | `multiply` の 1.05 と 1.15 を同じ属性で選ぶと、合計が `×1.21` と出る(計算の単体テスト) |
| `AC-BLD-03` | `percent_add` の 4 と 6 を同じ属性で選ぶと、合計が `+10%` と出る |
| `AC-BLD-04` | `flat_add` の `per_sec` の 2 を選ぶと、合計が `+2/秒` と出る |
| `AC-BLD-05` | `special` の効果を選ぶと、合計の数ではなく効果の名前が出る |
| `AC-BLD-06` | 属性の違う 2 つの `multiply` は、別の行に出る |
| `AC-BLD-07` | 深層効果「物理攻撃力上昇+0〜4(深層)」でランク 3 を選ぶと、「この段からデメリットが付く」が出る |
| `AC-BLD-08` | 通常効果の枠の選択の欄に、深層効果が出ない |
| `AC-BLD-09` | 「取得ルーン減少」(×0.9)を選ぶと、合計が `ember` の色で出る |
| `AC-BLD-10` | 効果を選び直しても、`/api/v1/relic-effects` が再び呼ばれない |

## 8. 未決事項

- **掛け算と % の足し算が同じ属性にかかるときの合わせ方**: 例えば物理攻撃力に ×1.05(通常)と +10.5%(深層)がかかるとき、今は別の行に出す。1 つの倍率(1.05 × 1.105)にまとめるかは、ゲームの中の計算の順を確かめてから決める。
- **共有の URL**: 旧版の画面設計にあった、選んだ組み合わせを URL のクエリに入れて共有する機能を作るか。作るなら P1 とする。
- **遺物の単位での選択**: 実際のゲームでは遺物ごとに効果の組が決まっている。遺物のマスタを持つかは、データの集め方が決まってから決める。
