# 共通設計: CI/CD と AWS への配置

流れの図は [CI/CD の流れ](../deploy.html) にある。
図とこの文書が食い違ったら、この文書が正しい。

## 1. 目的

PR を出してから本番に届くまでを、人の手順に頼らずに同じ順で進める。
データベースの更新で記録を失わないこと、壊れたものを本番に出さないことを、各段階の検査で確かめる。

## 2. 範囲

やること:

- AWS の上の配置と、環境の分け方
- PR、`main` へのマージ、リリースのそれぞれで走らせる検査と配置
- データベースの更新(マイグレーション)の流れ、規則、戻し方
- テストの計画

やらないこと:

- ワークフローと IaC の実装。この設計の承認の後に、別の Issue で行う
- 監視と通知の詳しい設計。8 章に挙げる

## 3. 画面

なし。

## 4. API

新しい API はない。
配置の後の確かめ(6.4)では、今ある API を呼ぶ。

## 5. AWS の上の配置

### 5.1 構成

手元の compose と同じ 6 つの部品を、次のように置く(決定の記録 [0014](../decisions/0014-deploy-to-aws-ecs.md))。

| 部品 | 置く場所 | 外から届くか |
|---|---|---|
| 入口 | CloudFront と ALB。HTTPS の証明書は ACM | はい |
| frontend | ECS on Fargate | ALB から |
| gateway | ECS on Fargate | ALB から |
| master、record、relic | ECS on Fargate。非公開のサブネット | いいえ。ECS Service Connect で gateway と record からだけ呼ぶ |
| データベース | RDS for PostgreSQL 16。1 台に 3 つのデータベース | いいえ。サービスのタスクからだけ |
| 秘密の値 | Secrets Manager。タスクの起動のときに環境変数として渡す | いいえ |
| イメージ | ECR。部品ごとに 1 つのリポジトリ | いいえ |

- ALB は `/api/` で始まる要求を gateway に、ほかを frontend に送る。
- `/internal/v1` は gateway が振り分けないので、外からは届かない(API の共通仕様 4.8)。
- データベースと利用者の分け方は、手元と同じにする(データベースの共通仕様 5.1)。最初に 1 回だけ、`db/init/` と同じ手順を管理者の資格で走らせる。

### 5.2 環境

| 環境 | 用途 | 配置の契機 | 承認 |
|---|---|---|---|
| ステージング | 本番と同じ形で確かめる | `main` へのマージ | 要らない |
| 本番 | 公開 | `v` で始まるタグ(例: `v1.2.0`) | GitHub の Environment で利用者が承認する |

- 2 つの環境は、同じ形を IaC で作る。大きさ(タスクの数、RDS の大きさ)だけを変える。
- 本番は、ステージングで確かめたイメージを、作り直さずにそのまま使う。イメージの名前は git のコミットの値にする。

### 5.3 AWS への権限

- GitHub Actions は OIDC で IAM のロールを引き受ける。期限のない鍵を GitHub に置かない。
- ロールは環境ごとに分け、本番のロールは `production` の Environment からだけ引き受けられるようにする。

## 6. パイプライン

### 6.1 PR のとき

すべて通らないとマージできない(ブランチの保護で必須にする)。

| 検査 | 内容 |
|---|---|
| frontend | 型検査、lint、Vitest、`next build` |
| backend | ビルド(警告を誤りとして扱う)、単体と結合と層のテスト。本物の PostgreSQL のコンテナに対して走らせる |
| gateway | ビルドとテスト |
| マイグレーション | 6.3 の検査 |
| イメージ | 6 つのイメージをビルドする(送らない)。Trivy で HIGH 以上の脆弱性があれば落とす |
| 一式の結合 | compose で一式を起動し、Playwright で主な流れ(7.2)を通す |
| 秘密の値 | gitleaks で、秘密の値が差分に入っていないかを確かめる |

変わったディレクトリの検査だけを走らせる。
ただし、マイグレーションと一式の結合は、`backend/`、`gateway/`、`frontend/`、`docker-compose.yml` のどれかが変わったら走らせる。

### 6.2 `main` へのマージのとき(ステージング)

1. 6 つのイメージと、サービスごとのマイグレーションの束(6.3)をビルドし、ECR へ送る。
2. ステージングのデータベースへマイグレーションを適用する(6.3)。
3. サービスを、master、record、relic、gateway、frontend の順に入れ替える。
4. 配置の後の確かめ(6.4)と、ステージングに対する Playwright を走らせる。

どこかで失敗したら、その後の段階に進まない。

### 6.3 データベースの更新

**適用の仕方**: ステージングと本番では、サービスの起動のときにマイグレーションを適用しない。
配置の前に、サービスごとのマイグレーションの束(`dotnet ef migrations bundle`)を ECS の単発のタスクで走らせて適用する(決定の記録 [0015](../decisions/0015-migrate-before-deploy.md))。
同じサービスのタスクを複数動かすと、起動のときの適用が競合するためである(データベースの共通仕様 5.5)。
手元の compose では、今のとおり起動のときに適用する。
どちらで動かすかは、環境変数 `Database__MigrateOnStartup` で切り替える。

**順序**: 本番では、適用の前に RDS の手動のスナップショットを取る。
適用は master、record、relic の順に、1 つずつ行う。
1 つでも失敗したら、サービスを入れ替えずに止める。

**互換の規則**: マイグレーションは、1 つ前の版のサービスのコードでも動く形にする。
入れ替えの間は古いタスクと新しいタスクが同時に動き、またコードだけを前の版に戻すことがあるためである。

| 変更 | やり方 |
|---|---|
| 列やテーブルを足す | 1 回で足す。`NOT NULL` の列は既定値を付ける |
| 列やテーブルを消す | 2 回の版に分ける。先にコードから使うのをやめて出し、次の版で消す |
| 列の名前や型を変える | 新しい列を足し、写し、コードを替えた後の版で古い列を消す |
| 制約を強める | 今ある行が満たすことを確かめるマイグレーションを先に出す |

記録の行を消すマイグレーションは書かない(決定の記録 [0005](../decisions/0005-keep-play-records.md))。

**PR での検査**:

| 検査 | 落とす条件 |
|---|---|
| 作り忘れ | `dotnet ef migrations has-pending-model-changes` が、モデルとマイグレーションの食い違いを見つけた |
| 書き換え | `main` にあるマイグレーションのファイルが変わった(モデルのスナップショットを除く) |
| 壊す変更 | 足したマイグレーションに `DropTable`、`DropColumn`、`RenameColumn`、`RenameTable` があり、PR に `db-breaking` の印がない |
| 前の版からの適用 | `main` のマイグレーションを適用し、初期データと試しの記録を入れたデータベースに、PR のマイグレーションを適用できない |
| 空からの適用 | 空のデータベースに、すべてのマイグレーションを適用できない(`AC-DB-01`) |

PR には、足したマイグレーションの SQL(`dotnet ef migrations script --idempotent`)を成果物として添え、レビューで読めるようにする。

### 6.4 配置の後の確かめ

| 確かめること | 期待する結果 |
|---|---|
| `GET /api/v1/bosses` を Gateway に送る | 200 と、空でない配列 |
| `GET /api/v1/patterns?bossId=gladius&spawnPointId=1` | 200 |
| `POST /internal/v1/references/resolve` を Gateway に送る | 404(`AC-ADM-20`) |
| 各サービスの `/health` | ECS のヘルスチェックが通る |

確かめは記録を保存しない。
本番に試しの記録を残さないためである。

### 6.5 リリースのとき(本番)

1. `v` で始まるタグを付けると、本番の配置のワークフローが待ちに入る。
2. 利用者が GitHub の Environment で承認する。
3. RDS のスナップショットを取り、マイグレーションを適用する(6.3)。
4. ステージングと同じイメージで、サービスを同じ順に入れ替える。
5. 配置の後の確かめ(6.4)を走らせる。

### 6.6 戻し方

| 失敗 | 戻し方 |
|---|---|
| 新しいタスクがヘルスチェックを通らない | ECS の配置のサーキットブレーカーが、前のタスク定義へ自動で戻す |
| 配置の後に誤りが見つかった | 配置のワークフローを、前の版のコミットの値で手で走らせる。データベースは戻さない(互換の規則で、前の版のコードが動く) |
| マイグレーションが途中で失敗した | サービスは入れ替わっていない。直したマイグレーションを足して出し直す |
| データが壊れた | 6.5 で取ったスナップショットか、RDS の指定時刻への復元で、新しいインスタンスを作って切り替える |

本番で `Down` のマイグレーションは走らせない。

## 7. テストの計画

### 7.1 段階ごとの検査

| 段階 | 走らせるもの | 何を守るか |
|---|---|---|
| 書いている間 | 道具のコンテナで、型検査、lint、テスト | 壊したことにすぐ気付く |
| PR | 6.1 のすべて | 壊れたものを `main` に入れない |
| `main`(ステージング) | マイグレーションの適用、配置の後の確かめ、Playwright | 本番と同じ形で動く |
| リリース(本番) | マイグレーションの適用、配置の後の確かめ | 公開しているものが動く |

### 7.2 一式の結合のテスト(Playwright)

PR では compose の一式に、ステージングでは配置したものに対して走らせる。

| 流れ | 確かめること | 受け入れ条件 |
|---|---|---|
| パターン検索 | 夜の王と開始地点を選ぶと、一覧が出る | `AC-PAT-10` |
| 記録して検索 | 記録を保存すると、同じ条件の件数が 1 増える | `AC-REC-08` |
| 記録の保存の失敗 | record-service を止めて保存すると、入力が残る | `AC-REC-14`(PR のときだけ) |
| 管理の鍵 | 鍵なしで管理の API を呼ぶと 401 | `AC-ADM-09` |

ステージングで記録を保存する流れは、試しの記録だと分かる備考を付ける。

## 8. 受け入れ条件

| 識別子 | 条件 |
|---|---|
| `AC-CD-01` | エンティティを変えてマイグレーションを足さない PR は、マイグレーションの検査で落ちる |
| `AC-CD-02` | `main` にあるマイグレーションのファイルを書き換えた PR は、マイグレーションの検査で落ちる |
| `AC-CD-03` | `DropColumn` を含むマイグレーションを足した PR は、`db-breaking` の印がなければ落ちる |
| `AC-CD-04` | `main` へマージすると、ステージングにマイグレーションが適用され、配置の後の確かめが通る |
| `AC-CD-05` | マイグレーションの適用が失敗すると、サービスのタスク定義が入れ替わらない |
| `AC-CD-06` | `v` のタグを付けても、利用者が承認するまで本番の配置が始まらない |
| `AC-CD-07` | 本番の配置では、マイグレーションの前に RDS のスナップショットができている |
| `AC-CD-08` | 本番に配置したイメージの名前が、ステージングで確かめたイメージの名前と同じである |
| `AC-CD-09` | ヘルスチェックを通らないイメージを配置すると、前のタスク定義に戻る |
| `AC-CD-10` | GitHub のリポジトリの秘密の値に、AWS の期限のない鍵がない |
| `AC-CD-11` | `Database__MigrateOnStartup=false` で起動したサービスは、未適用のマイグレーションがあっても適用しない |

## 9. 未決事項

- **IaC の道具**: Terraform にするか、AWS CDK にするか。決定の記録 0014 では Terraform を選んだが、利用者の承認を待つ。
- **監視と通知**: CloudWatch のアラームと、失敗の通知の先。本番を公開する前に決める。
- **費用**: タスクと RDS の大きさ。見込みは本番を公開する前に出す。
- **本番の公開の時期**: マップ画像の権利は決まった(決定の記録 [0016](../decisions/0016-publish-game-images.md))。本番を作る時期は利用者が決める。それまでは、ステージングを利用者が許した相手だけが見られるようにする。
