# ナイトレイン 収縮パターン帳 要件定義書

作成日: 2026-10-17

2026-03-16 版(バックエンドが Spring Boot の構成)と、その後の NestJS への移行を、本書で置き換える。
旧版はコミット `6529442` より前の履歴に残っている。

## 1. 目的と背景

エルデンリング ナイトレインのプレイ中に、マップの収縮(夜の雨)が起きた場所を記録し、同じ条件のプレイで過去の収縮先を見られるようにする。
条件は「夜の王(ボス)」「開始地点」「地変」の組み合わせである。

収縮先をアルゴリズムで予測しない。
実際のプレイで記録した収縮先を、そのまま見せる。

```
【初めての条件】
  ボス、地変、開始地点を選ぶ
  → 過去の記録がない
  → プレイしながら収縮先を入力し、保存する

【2 回目以降の同じ条件】
  ボス、地変、開始地点を選ぶ
  → 過去の収縮先を、パターンごとにすべてマップに出す
  → プレイの後に、今回の収縮先を足す
```

あわせて、遺物の効果を組み合わせたときの合計を計算するビルドシミュレーターを持つ。

### 2.2 対象としない機能

- 収縮先の予測の計算
- 利用者のアカウント。記録は誰のものかを区別せずに蓄える
- 記録の削除と修正の画面。誤った記録は備考で補う(決定の記録 [0005](decisions/0005-keep-play-records.md))
- 深き夜モードの記録
- 記録の書き出し(CSV)

## 3. 利用者と権限

| 利用者 | できること |
|---|---|
| プレイヤー | マップとパターンを見る。記録を足す。ビルドシミュレーターを使う |
| 管理者 | プレイヤーのできることに加えて、マスタの座標を登録、修正し、要らない行を非表示にする |

プレイヤーはログインしない。
管理者の操作は、Gateway が管理用の鍵(`X-Admin-Key`)を確かめた要求だけを受け付ける(決定の記録 [0009](decisions/0009-admin-key.md))。
鍵は環境変数 `ADMIN_KEY` に置き、管理者だけが知る。

管理者の判定は Gateway で行う。
各サービスは、サービス間キーで Gateway を通ったことを確かめる。
画面で管理の入口を隠すことは、権限の判定にならない。

## 4. ゲームの前提

### 4.1 1 回のプレイの流れ

```
1 日目(昼) → 1 日目(夜、夜ボス) → 2 日目(昼) → 2 日目(夜、夜ボス) → 3 日目(夜の王)
```

3 日目は専用の場所で戦うので、収縮を記録するのは 1 日目と 2 日目だけである。

### 4.2 収縮

1 日目と 2 日目の昼に、それぞれ 2 段階の収縮が起きる。

| 段階 | 始まり | 終わり |
|---|---|---|
| 第 1 次収縮 | 約 4 分 30 秒 | 約 7 分 40 秒 |
| 第 2 次収縮 | 約 11 分 10 秒 | 約 14 分 10 秒 |
| 夜ボスの出現 | 約 16 分 10 秒 | |

時間はコミュニティの情報によるもので、このアプリでは確かめていない。

- 第 1 次収縮は、12 か所の収縮候補地のどれかに向かう。
- 第 2 次収縮は、第 1 次収縮の円の中の 1 点に向かう。この点を第二収縮地点と呼ぶ。
- 1 日目と 2 日目の収縮先は、離れた場所になるとされる。
- 地変があるときは、2 日目の収縮先が地変の場所に寄るとされる。

### 4.3 マップの上の場所

| 種類 | 内容 | このアプリでの扱い |
|---|---|---|
| 開始地点 | プレイの始まりの場所。近くに教会か野営地がある | マスタ。座標と名前 |
| 収縮候補地 | 第 1 次収縮の円。12 か所 | マスタ。中心の座標と半径 |
| 第二収縮地点 | 第 2 次収縮の向かう点 | マスタ。座標 |
| 拠点候補地 | 毎回違う施設(小砦、大教会、遺跡など)が出る場所と、強敵の出る場所 | マスタ。地変ごとの座標と、大拠点、小拠点、強敵の種類。施設の種類は記録しない |
| 大拠点 | 多くの敵と、潜在する力を落とすボスがいる拠点。wiki の地図の赤の丸 | 拠点候補地の種類 |
| 小拠点 | 敵がいないか少ない拠点(教会、魔術師塔、村、野営地)。wiki の地図の青の丸 | 拠点候補地の種類 |
| 強敵 | フィールドボス。出る場所は決まっていて、出るボスは毎回変わる | 拠点候補地の種類。ボスの名前は持たない |

### 4.4 夜の王と地変

夜の王は 10 体、地変は 5 種類をマスタに持つ。
一覧は [データベースの共通仕様](design/common-database.md) の初期データの節に書く。

## 5. 機能要件

ここには機能の要点と、合否の判定の主なものだけを書く。
受け入れ条件の全体と識別子は、各機能の仕様書に書く。

### 5.1 マップ表示

- すべての座標を 1024 四方の座標空間の数で持つ。マップ画像(1000 px 四方)は、この座標空間いっぱいに引き伸ばして描く(決定の記録 [0004](decisions/0004-pixel-coordinates.md))。
- 地変を選ぶと、その地変のマップ画像に替える。
- 拡大は 0.3 倍から 3 倍まで、ドラッグで移動できる。
- 収縮のパターンは、色だけでなく番号でも見分けられるようにする。

### 5.2 パターン検索

- ボスと開始地点を選ぶと検索する。地変は選ばなくてよく、選ばないときは地変なしの記録だけを探す。
- 収縮先の並び(日、段階、場所)が同じ記録を 1 つのパターンにまとめ、記録の数と最後に記録した日時を出す。
- パターンは記録の数の多い順に並べる。
- 記録がないときは、記録を促す文言を出す。

### 5.3 プレイ記録

- 1 日目と 2 日目の、第 1 次と第 2 次の収縮先を、マップを押して選ぶ。第 1 次は収縮候補地、第 2 次は第二収縮地点で選ぶ(決定の記録 [0008](decisions/0008-second-shrink-by-point.md))。
- 4 つのうち 1 つ以上を選べば保存できる。途中で終わったプレイも記録できる。
- 1 日目と 2 日目の夜ボスを、任意で選べる。拠点の種類は記録しない(決定の記録 [0010](decisions/0010-night-boss-in-record.md))。
- 入力中の内容はブラウザに残し、ページを閉じても戻せる。
- 保存すると、すぐにパターン検索の結果に入る。

### 5.4 マスタの管理

- 管理の画面で、マップを押した場所の座標を取り、名前を付けて登録する。
- 登録した点を押すと、修正と非表示ができる。
- マスタの行は消さない。非表示にした行は、プレイヤーの画面と新しい記録の入力から外れ、過去の記録には残る(決定の記録 [0013](decisions/0013-hide-masters-instead-of-delete.md))。

### 5.5 ビルドシミュレーター

- 通常効果 3 枠と深層効果 3 枠に、遺物の効果とランクを選ぶ。
- 計算の種類(掛け算、% の足し算、固定値の足し算)ごとに、属性ごとの合計を出す。
- 計算はブラウザで行う。バックエンドは効果のマスタを返すだけである。

## 6. 非機能要件

- **動かし方**: `docker compose up --build` の 1 つのコマンドで一式が起動する。
- **対応する画面**: 幅 360px から崩れずに表示し、片手で操作できる。プレイ中にスマートフォンで使うことを想定する。
- **見た目**: エルデンリングの世界に合わせた暗い配色と装飾にする。決まりは [画面の共通仕様](design/common-frontend.md) に書く。
- **色覚**: パターンの色分けは、色覚の多様性に配慮した色の組を使い、番号でも見分けられるようにする。
- **応答の速さ**: 条件を選んでからパターンが出るまでを 1 秒以内にする(見込み。記録が 1 万件までの想定で、測っていない)。
- **データの扱い**: 記録は消さない(決定の記録 [0005](decisions/0005-keep-play-records.md))。
- **セキュリティ**: バックエンドのサービスは Gateway の外から呼べない。入力は各サービスで検証する。秘密の値をリポジトリに置かない。手元の外に公開するときは HTTPS で配る。管理用の鍵が見出しに平文で載るためである。
- **言語**: 画面は日本語だけとする。

## 7. 技術構成

| 役割 | 採用 |
|---|---|
| 画面 | Next.js 15(App Router)+ React 19 + TypeScript + Tailwind CSS 4。マップは react-konva |
| 入口 | ASP.NET Core 10(Minimal API)+ YARP。CORS、管理用の鍵の確認、3 つのサービスへの振り分け |
| バックエンド | ASP.NET Core 10(Minimal API)+ C# の 3 つのサービス。どれもクリーンアーキテクチャ(Domain、Application、Infrastructure、Api) |
| データアクセス | EF Core(Npgsql) |
| テーブルの変更管理 | EF Core Migrations |
| データベース | PostgreSQL 16 の 1 台に、サービスごとのデータベース。スキーマ `game` |
| テスト | バックエンドは xUnit、画面は Vitest |
| 実行環境 | Docker Compose |

バックエンドを .NET で作り直した理由は決定の記録 [0001](decisions/0001-dotnet-backend.md)、サービスを分けた理由は [0012](decisions/0012-split-services-by-feature.md)、クリーンアーキテクチャにした理由は [0011](decisions/0011-clean-architecture.md) に書く。

### 構成とデータの持ち主

```
Next.js (3000) → .NET Gateway (8080) → 3 つのサービス(master、record、relic) → PostgreSQL (5432)
```

| サービス | 受け持つもの | 持つデータ |
|---|---|---|
| `frontend` | 画面。ビルドシミュレーターの計算 | なし。入力中の記録をブラウザに持つ |
| `gateway` | 入口。CORS、管理用の鍵の確認、パスによる振り分け、サービス間キーの付与 | なし |
| `master-service`(8081) | マスタの取得、マスタの管理 | `nightreign_master`: 夜の王、地変、開始地点、収縮候補地、第二収縮地点、拠点候補地、夜ボス |
| `record-service`(8082) | プレイ記録、パターン検索 | `nightreign_record`: 記録、収縮先 |
| `relic-service`(8083) | ビルドシミュレーターの効果のマスタ | `nightreign_relic`: 遺物の効果 |
| `db` | データの保存 | サービスごとのデータベース |

決まりは次のとおりとする。

- 画面は Gateway だけを呼ぶ。3 つのサービスのポートはコンテナの外に出さない。
- Gateway は各サービスへの要求に `X-Service-Key` を付ける。各サービスはこの値が合わない要求を 401 で拒む。
- 各サービスは自分のデータベースだけに触れる。ほかのサービスのデータが要るときは、そのサービスの API を呼ぶ。
- サービスの間の呼び出しは、`record-service` から `master-service` への一方向だけにする。
- Gateway は `/api/v1/admin` の下への要求に `X-Admin-Key` を求め、合わない要求を 401 で拒む。
- Gateway はデータベースに触れない。
- Gateway とサービスを 1 つにまとめない理由は、決定の記録 [0002](decisions/0002-keep-gateway-separate.md) に書く。

### ディレクトリ構成

```

db/init/                         # サービスごとのデータベースと利用者を作る手順
docs/

docker-compose.yml
```

## 8. データモデル

| テーブル | 内容 | 種類 |
|---|---|---|
| `bosses`、`boss_weaknesses` | 夜の王と弱点の属性 | マスタ |
| `jihen` | 地変 | マスタ |
| `shrink_zones` | 収縮候補地 | マスタ |
| `second_shrink_points` | 第二収縮地点 | マスタ |
| `spawn_points` | 開始地点 | マスタ |
| `base_points` | 拠点候補地。マップごと。大拠点、小拠点、強敵の種類を持つ | マスタ |
| `night_bosses` | 1 日目と 2 日目の夜ボス | マスタ |

## 9. API

パスはすべて `/api/v1` の下に置く。
画面からは Gateway の 8080 番を通して呼ぶ。

| メソッドとパス | 内容 | 必要な役割 |
|---|---|---|
| `GET /api/v1/bosses` | 夜の王の一覧 | なし |
| `GET /api/v1/jihen` | 地変の一覧 | なし |
| `GET /api/v1/shrink-zones` | 収縮候補地の一覧 | なし |
| `GET /api/v1/second-shrink-points` | 第二収縮地点の一覧 | なし |
| `GET /api/v1/spawn-points` | 開始地点の一覧 | なし |
| `GET /api/v1/base-points?mapId=` | 拠点候補地の一覧 | なし |
| `GET /api/v1/night-bosses` | 夜ボスの一覧 | なし |
| `GET /api/v1/relic-effects` | 遺物の効果の一覧 | なし |
| `GET /api/v1/patterns` | パターン検索 | なし |
| `POST /api/v1/play-records` | 記録を保存する | なし |
| `GET`、`POST`、`PUT /api/v1/admin/...` | マスタの座標の管理と非表示 | 管理者(`X-Admin-Key`) |

`/api/v1/patterns` と `/api/v1/play-records` は `record-service`、`/api/v1/relic-effects` は `relic-service`、そのほかは `master-service` が受け持つ。
サービスの間だけで使う API(`/internal/v1`)は、[API の共通仕様](design/common-api.md) 4.8 に書く。

入出力とエラーは、[API の共通仕様](design/common-api.md) と各機能の仕様書に書く。

## 11. 段階

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| 0 | 共通の部品と `master-service` の土台 | 共通の部品、`master-service` の骨組み、マイグレーションと初期データ、プレイヤー向けのマスタの API ができ、Gateway の振り分けを通して返る |
| 1 | `record-service`(パターン検索とプレイ記録) | `master-service` の内部の API と `record-service` ができ、パターン検索とプレイ記録の受け入れ条件のうち API の条件が通る |
| 2 | マスタの管理と権限 | Gateway が管理用の鍵を確かめ、マスタの管理の受け入れ条件が通る |
| 3 | 画面の見た目の作り直し | 画面の共通仕様の受け入れ条件が通る。4 つの画面が新しい見た目になる |
| 4 | `relic-service`(ビルドシミュレーターの API) | ビルドシミュレーターの受け入れ条件が通る |
| 5 | P1 の機能 | 収縮のタイムライン、オフラインでの利用 |

段階 3(画面の見た目)は、2026-10-17 に利用者が決め、段階 1 と並べて進める。
記録の入出力の形を変える画面の直し(第 2 次を第二収縮地点で、夜ボス)は段階 1 で行い、見た目の作り直しは段階 3 で行う。
段階ごとに、受け入れ条件のテストが通ってから次へ進む。
